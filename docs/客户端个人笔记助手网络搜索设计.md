# 客户端个人笔记助手网络搜索设计

开发设计稿 · 2026-11-28 · 对应任务 `FEAT-20261128-pi-web-access`

## 1. 方案结论

WeNote 个人笔记助手使用内部 `AgentTool` 实现网络相关工具，搜索能力通过 OpenAI Responses API 的原生 `web_search` 工具提供。

Agent 继续由 `@earendil-works/pi-agent-core` 驱动。文档工具和网络工具都在 `runTurn` 中注册为 `AgentTool`，模型通过统一的工具循环调用它们。

目标调用链如下。

```text
WeNote Pi Agent Core
        ↓
内部 AgentTool
        ↓
WebSearchService
        ↓
OpenAI Responses API
        ↓
web_search
        ↓
搜索文本与来源
```

网络搜索采用客户端内部工具直连方式。

- Web、Android、iOS 和桌面端都在客户端注册内部 `AgentTool`
- `AgentTool.execute()` 直接调用 OpenAI Responses API
- 复用当前助手的 Base URL、模型 ID 和 API Key
- 不新增服务器端搜索接口
- 不配置外部 MCP Gateway 地址

本方案保留 OpenAI-compatible endpoint 配置能力。此前受控验证使用过以下配置。

- Base URL：`https://api.ergou.vip/v1`
- Responses endpoint：`https://api.ergou.vip/v1/responses`
- 已验证模型：`gpt-6.2-sol`
- 搜索工具：`web_search`

API Key 只在客户端配置、请求内存或 Tauri 运行时中使用，不进入仓库、任务记录、Agent prompt、会话正文和普通日志。

## 2. 目标和范围

### 2.1 用户目标

用户可以在笔记助手中提出需要联网查询的问题。Agent 根据需要调用网络工具，生成回答并展示可点击的来源。

网络搜索结果用于当前回答和当前会话上下文。搜索结果不会自动写入笔记。用户要求整理到笔记时，仍然进入现有的读取、预览和确认写入流程。

### 2.2 首轮工具范围

首轮实现以下内部工具。

| 工具 | 用途 | 网络请求 |
| --- | --- | --- |
| `web_search` | 使用 OpenAI Responses API 搜索互联网并返回摘要与来源 | 调用 OpenAI `web_search` |
| `get_search_content` | 读取当前轮次已缓存的搜索结果文本 | 读取本地轮次缓存 |
| `fetch_content` | 读取用户或搜索结果指定的网页正文 | 由客户端发起受控 HTTP 请求 |
| `source_check` | 对指定来源进行复核并返回判断依据 | 调用 OpenAI `web_search` 或受控网页读取 |

`web_search` 是首轮必须完成的能力。其余工具与 `web_search` 共用参数校验、超时、取消、来源归一化和错误处理框架。

### 2.3 平台范围

- Web、Android、iOS 和桌面端都使用客户端内部网络工具
- 各端共享工具定义、OpenAI Responses 请求格式、结果模型、来源展示和历史记录格式
- Web 和移动端使用当前前端运行环境的 HTTPS 请求能力
- 桌面端可以使用同一套前端请求适配，也可以由 Tauri 提供请求转发

## 3. 与现有 Agent 架构的衔接

### 3.1 Pi Agent Core 的职责

`pi-agent-core.Agent` 负责以下工作。

1. 接收模型输出
2. 识别工具调用
3. 按工具名称匹配 `AgentTool`
4. 调用 `execute`
5. 将工具结果放回上下文
6. 继续生成回答

文档工具和网络工具都使用这一套机制。Agent 不需要感知底层是本地库、Tauri 命令还是服务器 HTTP 请求。

### 3.2 文档工具现有链路

```text
runTurn
  ↓
assistantRpc("tools/list")
  ↓
转换为 AgentTool
  ↓
assistantRpc("tools/call")
  ↓
Connections.tsx
  ↓
Library.run()
```

文档编辑会继续使用当前的版本校验、操作幂等、预览和用户确认流程。

### 3.3 网络工具目标链路

```text
runTurn
  ↓
createWebSearchTools()
  ↓
AgentTool.execute()
  ↓
WebSearchService
  ├─ Web / Android / iOS → OpenAI Responses API
  └─ Desktop → OpenAI Responses API，必要时经 Tauri command
```

网络工具不执行 `initialize`、`tools/list`、`tools/call` 和 MCP 会话管理。工具 schema 由 WeNote 代码固定定义，参数校验由客户端 TypeScript 代码完成。

## 4. 内部工具设计

### 4.1 工具定义

工具定义放在 `apps/web/src/assistant/webSearch.ts`，由 `createWebSearchTools()` 返回 `AgentTool[]`。

```ts
export type WebSearchToolName =
  | "web_search"
  | "get_search_content"
  | "fetch_content"
  | "source_check";
```

每个工具需要提供以下字段。

- `name`
- `label`
- `description`
- `parameters`
- `execute`

`execute` 只负责调用 `WebSearchService`、更新状态和转换结果。网络请求、响应解析和来源提取放在服务层，避免将 HTTP 细节写入 Agent 生命周期代码。

### 4.2 `web_search`

输入参数建议如下。

```ts
{
  query: string;
  domains?: string[];
  recency?: "day" | "week" | "month" | "year";
  search_context_size?: "low" | "medium" | "high";
}
```

参数规则如下。

- `query` 必填，长度限制为 1 至 4000 个字符
- `domains` 最多 20 个，每个域名限制为合法主机名
- `recency` 转换为搜索提示或 endpoint 支持的过滤条件
- `search_context_size` 由搜索服务映射到当前 endpoint 支持的参数
- 未识别的扩展字段直接拒绝

搜索服务向 Responses endpoint 发起请求。请求结构的核心部分如下。

```json
{
  "model": "gpt-6.2-sol",
  "input": "用户搜索问题",
  "tools": [
    {
      "type": "web_search"
    }
  ]
}
```

客户端不把用户未引用的笔记正文加入 `input`。若用户明确引用笔记，Agent 可以根据现有引用规则将必要的上下文整理为搜索问题的一部分。

### 4.3 `get_search_content`

该工具读取当前 Agent 轮次已经产生的搜索结果。

搜索结果缓存只存在于当前 `runTurn` 的内存中，使用搜索请求 ID 或来源 URL 作为索引。缓存内容包括：

- 搜索摘要
- 来源标题
- 来源 URL
- 来源片段
- 搜索请求时间

历史消息只保存最终回答和来源记录。搜索缓存不会无限期写入会话历史。

### 4.4 `fetch_content`

该工具读取指定网页正文，供 Agent 对来源进行进一步核对。

客户端需要执行以下检查。

- 只允许 `http` 和 `https`
- 拒绝本机回环地址、私有地址、链路本地地址和元数据地址
- 限制响应大小
- 限制读取时间
- 只提取 `text/html`、`text/plain` 和明确支持的文本类型
- 去除脚本、样式和导航噪声
- 返回正文截断标记和原始 URL

网页内容不直接写入笔记。用户确认写入时，仍使用现有笔记工具。

### 4.5 `source_check`

该工具对来源进行复核。

输入包括来源 URL 和需要核对的判断。客户端可以先读取来源正文，再通过 Responses API 的 `web_search` 对相关信息进行交叉检索。返回内容包括：

- 判断结果
- 支持判断的来源
- 不确定因素
- 可继续核对的 URL

## 5. WebSearchService

### 5.1 TypeScript 接口

```ts
export type WebSearchService = {
  search(
    input: WebSearchInput,
    signal?: AbortSignal,
  ): Promise<WebSearchResult>;
  getSearchContent(
    input: GetSearchContentInput,
    signal?: AbortSignal,
  ): Promise<WebSearchResult>;
  fetchContent(
    input: FetchContentInput,
    signal?: AbortSignal,
  ): Promise<WebContentResult>;
  checkSource(
    input: SourceCheckInput,
    signal?: AbortSignal,
  ): Promise<SourceCheckResult>;
};
```

### 5.2 运行时适配器

`createWebSearchService()` 在客户端封装 OpenAI Responses API 请求。Web、Android、iOS 和桌面端返回相同的 `WebSearchResult`。

```text
AgentTool.execute()
  → createWebSearchService()
  → POST <baseUrl>/responses
  → OpenAI Responses API
  → web_search
```

桌面端可以直接使用前端请求，也可以由 Tauri 提供等价的 HTTP 转发。两种实现只属于传输差异，工具定义、参数校验、响应解析、来源展示和历史记录保持一致。

### 5.3 客户端配置

客户端复用当前助手模型设置中的：

- Responses Base URL
- API Key
- 搜索模型 ID

配置示例。

```text
Base URL: https://api.ergou.vip/v1
Responses endpoint: https://api.ergou.vip/v1/responses
Search model: gpt-6.2-sol
```

若 Base URL 已经包含 `/responses`，直接使用该地址。否则在 Base URL 后追加 `/responses`。API Key 只用于客户端请求，不写入 Agent prompt、工具结果、会话历史和普通日志。

Web、Android、iOS 需要目标 endpoint 允许客户端跨域请求。桌面端可以直接使用同一请求，也可以通过 Tauri 转发。

## 6. 客户端搜索请求设计

### 6.1 请求接口

内部 `WebSearchService` 直接向配置的 Responses endpoint 发起请求。

```text
POST <baseUrl>/responses
Authorization: Bearer <model API key>
Content-Type: application/json
```

请求体示例。

```json
{
  "model": "gpt-6.2-sol",
  "input": "OpenAI Responses API web search 的使用方式",
  "tools": [
    { "type": "web_search" }
  ]
}
```

客户端解析 Responses 输出中的文本和来源 annotation，转换为统一的 `WebSearchResult`。

### 6.2 网页读取和来源核验

`fetch_content` 和 `source_check` 首轮优先复用 OpenAI Responses API 的搜索结果和来源。如果需要直接读取网页，由客户端发起受控请求，并复用 URL、响应大小和内容类型限制。

客户端不能访问的网页由搜索 Provider 返回可用来源，不通过新增 WeNote API 绕过浏览器网络限制。

### 6.3 客户端错误响应

服务层将 HTTP 和 Responses 错误转换为稳定错误码。

```json
{
  "code": "SEARCH_PROVIDER_ERROR",
  "message": "搜索服务暂时不可用"
}
```

错误码至少包括：

- `SEARCH_DISABLED`
- `SEARCH_NOT_CONFIGURED`
- `SEARCH_AUTH_FAILED`
- `SEARCH_PROVIDER_ERROR`
- `SEARCH_TIMEOUT`
- `SEARCH_INVALID_ARGUMENT`
- `SEARCH_CONTENT_BLOCKED`
- `SEARCH_RATE_LIMITED`

错误消息提供给用户时需要截断提供商原始详情。完整错误只进入脱敏后的本地调试日志。

## 7. Agent 接入和状态反馈

`runTurn` 在联网搜索开关打开时注册网络工具。

```text
WeNote tools + WebSearch tools
        ↓
Agent.initialState.tools
```

工具调用状态如下。

- `web_search` 显示“正在搜索网络…”
- `get_search_content` 显示“正在读取搜索结果…”
- `fetch_content` 显示“正在读取网页…”
- `source_check` 显示“正在核验来源…”

搜索结果转换为 Pi Agent 工具结果。

```ts
{
  content: [
    { type: "text", text: result.text }
  ],
  details: null
}
```

同时向会话历史追加来源记录。

```ts
type WebSource = {
  title: string;
  url: string;
  snippet?: string;
  publishedAt?: string;
};
```

## 8. 配置界面

设置页保留以下配置。

- 启用网络搜索
- 搜索模型 ID，可选，默认使用当前模型
- 搜索服务状态

移除 Web Access MCP Gateway 地址配置。所有客户端直接使用当前模型配置访问 OpenAI Responses API。

搜索开关关闭时：

- 不创建 `WebSearchService`
- 不向 Agent 注册网络工具
- 不发起搜索 HTTP 请求
- 不加载搜索缓存

网络搜索配置变化后，需要更新助手上下文缓存键，避免旧上下文继续使用已关闭的工具。

## 9. 数据和权限

### 9.1 客户端

- 复用当前模型配置中的 API Key
- 不把 API Key 返回给 Agent、搜索结果或历史记录
- 不把完整网页正文写入普通日志
- 不把私有笔记正文自动发送到搜索服务
- 限制单次查询长度、响应大小、请求时间和并发数
- 停止对话时取消 HTTP 请求

### 9.2 服务器端边界

本方案不新增 WeNote 搜索 API，也不在 WeNote 服务端保存搜索 Key。现有 WeNote API 继续负责登录、笔记和同步。若未来需要服务端托管搜索 Key，应另行增加代理服务和权限设计。

### 9.3 笔记写入

网络工具只能返回工具结果和来源。任何新建、编辑、移动或删除笔记的请求继续经过：

```text
读取当前版本
  ↓
生成修改预览
  ↓
用户确认
  ↓
现有写入工具提交
```

## 10. 错误处理

需要覆盖以下情况。

- 客户端搜索未配置
- OpenAI API Key 无效
- Responses endpoint 不支持 `web_search`
- 搜索模型无权限
- OpenAI 服务返回错误
- 搜索超时
- 网页读取被安全策略拒绝
- 网页响应过大
- 用户停止对话
- 搜索成功但最终 Agent 回复失败
- 客户端模型配置失效

工具失败时保留用户输入和已经产生的笔记工具结果，允许用户重新发送。连续两次工具失败后沿用现有 Agent 停止策略。

## 11. 测试和验收

### 11.1 TypeScript 单元测试

- 工具开关关闭时不注册网络工具
- `web_search` 参数校验
- `fetch_content` URL 校验
- `source_check` 参数校验
- Responses 响应文本解析
- Responses 来源 annotation 解析
- 来源去重和 URL 清洗
- AgentTool 结果转换
- AbortSignal 取消传播
- HTTP 超时
- API Key 不进入历史记录和工具结果

### 11.2 客户端集成测试

- Web、Android、iOS 和桌面使用当前模型配置发起 Responses 请求
- 请求包含正确的模型、`web_search` 工具和查询文本
- API Key 只进入 Authorization 请求头
- HTTP 错误和 Responses 错误转换为稳定错误码
- 请求取消可以中断搜索
- 网页 URL、响应类型和响应大小限制生效

### 11.3 人工验收

1. 在当前助手模型配置中填写 Responses Base URL、API Key 和搜索模型。
2. 打开笔记助手的网络搜索开关。
3. 输入“搜索最新的 OpenAI Web Search 文档”。
4. 确认 Agent 调用了内部 `web_search` 工具。
5. 确认回答包含来源标题和可点击 URL。
6. 关闭联网搜索后发送同样问题，确认没有网络工具调用。
7. 搜索过程中点击停止，确认请求被取消。
8. 使用网页读取和来源核验，确认安全限制和错误提示生效。
9. 使用笔记写入请求，确认搜索结果不会跳过写入预览和用户确认。
10. 刷新并重新打开历史对话，确认来源仍然显示。

## 13. 交付边界

本次方案的交付目标是客户端内部网络工具和 OpenAI Responses Search 的完整调用链。运行环境继续使用现有 WeNote API，搜索请求由各端客户端直接发往配置的 Responses endpoint。

`pi-web-access` 的 MCP 适配代码和外部 Gateway 配置属于上一版实现记录。改造完成后，客户端网络搜索不再依赖它们。
