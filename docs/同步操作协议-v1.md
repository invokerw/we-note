# 同步操作协议 v1

> 状态：Phase 0 冻结稿
> 依据：[产品与技术设计](./产品与技术设计.md) 第 6、7、9、10.4、20、21、22、25 节与[设计评审记录](./设计评审记录.md)
> 可执行契约：[`tests/sync-fixtures/`](../tests/sync-fixtures) 与 [`tests/protocol/sync-v1.test.mjs`](../tests/protocol/sync-v1.test.mjs)

本文档冻结三个会影响跨端一致性的行为：

1. 同一 `operation_id` 重试时返回首次处理结果。
2. 内容提交按**目标文件**的基准版本判断冲突，`vault_revision` 只用于增量拉取。
3. 增量游标过旧时，通过 manifest 快照恢复。

服务端和客户端应当用同一组请求、初始状态和预期结果各自验证实现。本轮只冻结协议与契约样例；数据库、Blob 存储适配器、网络服务、客户端、三方合并和第 25 节端到端闭环不在本轮范围。

## 1. 范围与非目标

### 1.1 本轮冻结

- `vault_id` / `device_id` / `operation_id` / `file_id` 等标识的语义。
- `update_file_content` 的提交判定顺序与结果结构。
- `FILE_VERSION_CONFLICT` 与 `CURSOR_TOO_OLD` 两种错误的稳定结构与恢复字段。
- 增量拉取的游标边界（等于下界仍可增量，严格小于下界需快照恢复）。
- manifest 快照的必要条目。

### 1.2 明确不做

| 事项 | 说明 |
| --- | --- |
| 其余 11 种写入操作的可执行契约 | 第 9.3 节全部操作名在字段表中列出，但 v1 样例只冻结 `update_file_content`。其余操作返回 `OPERATION_NOT_SUPPORTED`。 |
| 上传会话接口 | 夹具用已完成的 `blob_reference` 表示上传结果，见第 10.4 节 `sync/upload-sessions`。 |
| 日志保留时长与配额 | 不影响本轮判断，夹具直接给出 `min_available_revision`。 |
| WebSocket 投递 | 只承担通知职责，不改变一致性判定，客户端始终可以通过 HTTP 增量拉取恢复。 |
| 三方合并算法 | 本轮只冻结冲突错误的可定位字段，合并本身留给后续任务。 |

## 2. 接口

沿用第 10.4 节的两个端点。主设计没有细分增量拉取的请求体，本协议约定用 `mode` 区分。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/v1/vaults/{vault_id}/sync/changes` | `mode: "submit"` 提交单个操作；`mode: "pull"` 按游标拉取增量 |
| `GET` | `/api/v1/vaults/{vault_id}/sync/manifest` | 获取重建文件映射所需的快照 |

约定：

- **方法与路径联合校验**：`sync/changes` 只接受 `POST`，`sync/manifest` 只接受 `GET`。方法按 HTTP 语义**精确匹配且区分大小写**：`post` / `get` 都不等于契约里的 `POST` / `GET`，一律返回 `METHOD_NOT_ALLOWED`。路径不属于协议返回 `ENDPOINT_NOT_FOUND`；路径存在但方法不符返回 `METHOD_NOT_ALLOWED`，`allowed_method` 给出该路径唯一合法的取值。
- **manifest 用无正文 GET**：`GET` 请求不携带请求体。`vault_id` 从路由读取；`device_id` 必须通过 `X-Device-Id` 请求头或 `device_id` 查询参数显式提供。若查询参数额外携带 `vault_id`，它必须与路由一致，否则返回 404 `VAULT_MISMATCH`。这是 Web 端唯一可行的调用方式——标准 `Request` 构造函数会直接拒绝带正文的 GET。
- **标识必填且类型严格**：`submit`、`pull` 的请求体必须显式携带非空字符串的 `vault_id` 与 `device_id`；`manifest` 的 `device_id` 同样必须显式提供。缺省、显式 `null`、空串或类型不对一律返回 `INVALID_REQUEST`，并在 `missing_fields` 中列出相应字段名；**缺失或类型错误不会被报成 `VAULT_MISMATCH`**。manifest 也不为缺失的 `device_id` 补 `null`，响应直接回显请求值。
- 路由中的 `{vault_id}` 必须等于请求体（`submit` / `pull`）中的 `vault_id`，否则返回 400 `VAULT_MISMATCH`。该判定发生在必填与类型校验之后：先确认标识都「有且合法」，再比较取值是否一致。因此「错误路由 + 缺失 `device_id`」必须先返回 `INVALID_REQUEST`，而不是 404 `VAULT_MISMATCH`。
- **请求适配层与公开支持范围**：契约模型接受两种请求表示——内部对象 `{ method, endpoint, headers, body, query }`，以及浏览器 / Node 的**标准 `Request`**。标准 `Request` 的 URL、请求头与**正文**都会被真正读取：`POST /sync/changes` 的 JSON 正文经 `clone().text()` + `JSON.parse` 解析，因此用标准 `Request` 携带 JSON 体提交不会退化成「缺字段请求」；同一个 `Request` 对象可被复用（每次都 `clone()`，不会因 body 已消费而读到空正文）。`GET /sync/manifest` 按契约是无正文请求，适配层不读取也不要求正文。正文不是合法 JSON 时返回 `INVALID_REQUEST` 并带 `body_error`。
- **字段来源严格分离**：请求头只来自 `headers`，查询串只来自 `query` / URL，请求体只来自 `body`。具体规则：
  - `manifest`（`GET`）**没有请求体**。`device_id` 有两个合法来源：`X-Device-Id` 请求头（优先，字段名大小写无关）或 `device_id` 查询参数。**只放请求头**是合法调用，实现不得把它复制成查询参数；执行器也不得把请求头内容塞进 URL。
  - 查询串额外携带 `vault_id` **允许存在**，前提是与路由一致；不一致才返回 404 `VAULT_MISMATCH`。实现不得因为「查询里出现了 `vault_id`」就无条件拒绝。
  - `submit` / `pull`（`POST`）的 `vault_id`、`device_id` 等业务字段**只来自请求体**。查询串不能为请求体补字段，也不能掩盖请求体里错误的 `vault_id`：请求体 `vault_id` 与路由不一致仍返回 400。任意无关查询字段（如 `?trace=abc`）不得影响请求体校验，也不得出现在响应里。
  - 请求体 `vault_id` 校验与查询串 `vault_id` 校验是**两条独立规则**，按各自的错误码与 HTTP 状态返回（请求体 400 / 查询串 404）。
- **全部响应（成功与错误）** 都包含 `protocol_version`（固定为 `sync-v1`）与 `request_id`，并携带定位字段 `endpoint`、`method`、`allowed_method`（端点不属于协议时 `allowed_method` 为 `null`，但字段本身必须存在）。`submit`、`pull`、`manifest` 三种成功响应同样必须携带这三个字段：它们回显实际请求路径、实际 HTTP 方法与该端点允许的方法，因此破坏成功响应里的任一定位字段也必须让契约测试失败。
- 提交类请求可携带 `Idempotency-Key`；若携带，其值必须等于 `operation_id`。请求头**字段名大小写无关**（`Idempotency-Key` 与 `idempotency-key`、`IDEMPOTENCY-KEY` 等价），实现必须按大小写无关方式查找。

## 3. 字段表

### 3.1 标识与版本

| 字段 | 类型 | 必填 | 可空 | 取值与含义 |
| --- | --- | --- | --- | --- |
| `vault_id` | string | 是 | 否 | 所属 Vault。由服务端分配的稳定标识。`submit` / `pull` 的请求体**必须显式提供非空字符串**且等于路由，查询串不能替代该字段；`manifest` 的取值直接来自路由，查询参数若重复携带**必须一致**（一致时允许存在）。缺省、`null`、空串或非字符串返回 `INVALID_REQUEST` 并把字段名列入 `missing_fields`，**不会**退化为 `VAULT_MISMATCH`。 |
| `device_id` | string | 是 | 否 | 发起本次操作的客户端实例标识，**非空字符串**。同一设备在同一 Vault 内保持不变。提交、拉取与 manifest 都**必须显式提供**，缺省、`null`、空串或非字符串返回 `INVALID_REQUEST`；manifest 响应回显该值，不补 `null`。 |
| `operation_id` | string | 是 | 否 | 一次逻辑操作的幂等键，**非空字符串**。同一 Vault 内重试必须复用原值；成功提交过的 `operation_id` 不可用于另一份请求内容。 |
| `file_id` | string | 是 | 否 | 稳定的文件身份，**非空字符串**。移动或重命名**不改变** `file_id`；定位文件只用 `vault_id` + `file_id`，不用路径。 |
| `operation` | string | 是 | 否 | 操作类型，**非空字符串**，取值见第 4 节。非字符串返回 `INVALID_REQUEST`；字符串但不在第 4 节枚举内返回 `OPERATION_NOT_SUPPORTED`。 |
| `path` | string | 是 | 否 | 规范化的 Vault 相对路径，`/` 分隔，NFC 规范化，禁止 `..`、`.`、空段、前导 `/`、反斜杠和 NUL。`update_file_content` 必须沿用目标文件当前路径。 |
| `base_revision` | integer | 是 | 否 | 提交方已经应用到本地的 Vault 游标，非负，语义是**写入前**的状态。一次成功写入占用 `vault_revision = N`，写入前的状态就是 `N-1`，因此历史首次请求必须满足 `base_revision <= N-1`；`base_revision = N` 或更大属于初态不自洽。在线提交只要求 `base_revision <= 当前 vault_revision`，**不代表**冲突判定依据。 |
| `last_server_revision` | integer | 是（`pull`） | 否 | 增量拉取起点，非负。只返回 `vault_revision` **严格大于**该值的 Change，按 revision 递增排列。 |
| `vault_revision` | integer | 否（响应） | 否 | Vault 当前变更序号，每次有效写入加一。变更顺序的唯一权威来源。**可安全表示的范围是 `0..Number.MAX_SAFE_INTEGER`（2^53-1）**：到达上界后**不能再安全地分配新的 revision**（`2^53` 已超出安全整数范围，继续加一会因浮点舍入停在同一个值上，等于「加一后复用同一个 revision」），此时提交返回 `REVISION_EXHAUSTED`（503）并保持状态不变。 |
| `min_available_revision` | integer | 否（响应 / 夹具） | 否 | 仍可用于增量拉取的最早游标。`last_server_revision == min_available_revision` 时仍可增量；`<` 时需要快照恢复。**只有字段缺省时才默认 `0`**：显式写 `null`（或 `undefined`、非整数）属于类型错误，加载阶段即拒绝，不会被 `?? 0` 静默当成「下界为 0」。 |

### 3.2 冲突判定（只针对目标文件）

| 字段 | 类型 | 必填 | 可空 | 取值与含义 |
| --- | --- | --- | --- | --- |
| `base_version_id` | string | 条件必填 | 是 | 提交方已应用的版本。与目标文件的 `current_version_id` 比对。 |
| `base_content_hash` | string | 条件必填 | 是 | 提交方已应用版本的完整内容 SHA-256，`sha256:<64 位小写十六进制>`。与目标文件**当前版本**的 `content_hash` 比对。 |

`base_version_id` 与 `base_content_hash` **至少提供一项**，否则返回 `BASE_REQUIRED`。**「提供」指存在非 `null` 值**：字段缺省、显式写 `null` 或两者皆为 `null` 都算未提供，不能靠两个 `null` 绕过冲突判定。已提供的值必须类型正确：`base_version_id` 为非空字符串，`base_content_hash` 匹配 `sha256:<64 位小写十六进制>`，否则返回 `INVALID_REQUEST`。两项都提供时**必须同时匹配**当前版本，任一项不匹配即 `FILE_VERSION_CONFLICT`。

### 3.3 内容与元数据

| 字段 | 类型 | 必填 | 可空 | 取值与含义 |
| --- | --- | --- | --- | --- |
| `blob_reference` | string | 是 | 否 | 已完成的待提交内容引用，**非空字符串**（夹具中以 `upload_` 前缀表示）。提交时服务端按此引用取回完整字节复核。类型错误返回 `INVALID_REQUEST`，引用不存在返回 `UPLOAD_NOT_READY`。 |
| `content_hash` | string | 是 | 否 | 完整**原始字节**的 `sha256:<64 位小写十六进制>`。按文件字节计算，不经过解析或重新序列化；JSON 样本同样按原始字节计算。提交时必须同时等于**实际取回字节**的 SHA-256 与 **completed 上传会话**记录的 `content_hash`，否则返回 `CONTENT_HASH_MISMATCH`。 |
| `content_size` | integer | 是 | 否 | 原始字节数，非负。必须同时等于实际取回字节数与 completed 上传会话记录的 `content_size`，否则返回 `CONTENT_SIZE_MISMATCH`（大小先于哈希判定）。 |
| `client_timestamp` | string | 是 | 否 | 客户端时间，RFC 3339 UTC，必须以大写 `Z` 结尾（例如 `2026-11-21T09:05:00Z`，允许 1–9 位小数秒）。**日期与时刻的取值逐项校验**：年份 4 位，月份 `01`–`12`，日期不得超过该年该月的实际天数（含闰年规则），`00`–`23` 时、`00`–`59` 分、`00`–`59` 秒。因此 `2026-02-29T09:05:00Z`（2026 非闰年）、`2026-04-31T09:05:00Z`、`2026-01-01T24:00:00Z` 都返回 `INVALID_REQUEST`，不能依赖宽松的日期解析静默进位。带时区偏移、小写 `z`、缺秒或非 RFC 3339 的写法同样返回 `INVALID_REQUEST`。仅作记录，**不决定**变更顺序。 |
| `metadata` | object | 是 | 否 | 格式信息。**必须是非空对象且必须包含 `format`**：缺省、`{}`、`format: null` 或 `format` 不在枚举内都返回 `INVALID_REQUEST`。`format` 取值 `md`、`txt`、`json`（后续可扩展）；`line_ending` 可选，取值 `lf`、`crlf`，出现时必须在枚举内，否则返回 `INVALID_REQUEST`。`format` 还必须等于目标文件格式，否则返回 `FORMAT_MISMATCH`。 |

### 3.4 响应字段

| 字段 | 类型 | 出现在 | 含义 |
| --- | --- | --- | --- |
| `protocol_version` | string | 全部 | 固定 `sync-v1`。 |
| `request_id` | string \| null | 全部 | 本次请求的追踪标识，格式 `req_` + **恰好** 6 位数字，序号范围 **1..999999**；`req_000000` 不是合法标识。**每次请求都新分配**。唯一例外是 `REQUEST_ID_EXHAUSTED`：序号已用尽时该字段显式为 `null`，绝不生成七位标识。 |
| `mode` | string | 成功响应 | `submit`、`pull` 或 `manifest`。**错误响应不携带该字段**；`MODE_REQUIRED` 用 `requested_mode` 回显被拒绝的取值。 |
| `replayed` | boolean | 提交响应 | 是否命中幂等账本并返回首次结果。 |
| `original_request_id` | string | 重放响应 | 首次处理该 `operation_id` 的 `request_id`。重放时 `request_id` 取本次新值，`original_request_id` 保留首次值。 |
| `version_id` | string | 提交响应 | 本次新建的文件版本。 |
| `parent_version_id` | string | 提交响应 | 新版本的父版本，即提交时目标文件的 `current_version_id`。 |
| `change_id` | string | 提交响应 | 本次写入产生的 Change。 |
| `blob_id` | string | 提交响应 | 新版本引用的 Blob，等于 `blob_` + **完整** SHA-256 的 64 位十六进制。内容寻址：同一 Vault 内只有完整哈希相同才复用同一个 Blob；仅前缀相同的不同字节必须得到不同 Blob。 |
| `vault_revision` | integer | 提交响应 | 本次提交占用的 revision，等于提交前 `vault_revision + 1`。 |
| `changes` | array | 拉取响应 | 严格晚于请求游标的 Change，按 revision 递增。 |
| `snapshot_revision` | integer | manifest | 快照对应的 `vault_revision`。恢复方从此值续拉。 |
| `files` | array | manifest | 重建映射所需条目，按 `path` 升序。 |
| `endpoint` | string \| null | 全部（成功 + 错误） | 本次请求打到的路径，原样回显；无法读取时为 `null`。 |
| `method` | string \| null | 全部（成功 + 错误） | 本次请求使用的 HTTP 方法，原样回显；缺省时为 `null`。 |
| `allowed_method` | string \| null | 全部（成功 + 错误） | 该端点唯一合法的方法（`changes` → `POST`，`manifest` → `GET`）；端点不属于协议时为 `null`。 |
| `body_error` | string | 错误 | 仅在请求体无法解析为 JSON 时出现，说明解析失败原因。 |
| `replayable` | boolean | `IDEMPOTENCY_KEY_REUSED` | `true` 表示该 `operation_id` 有可重放的首次结果；`false` 表示它来自历史 Change 或 `reserved_operation_ids`，只有占用关系而没有首次结果。 |

定位字段 `endpoint` / `method` / `allowed_method` 覆盖**所有**响应：`submit`（首次与重放）、`pull`、`manifest` 三种成功模式都必须出现，取值分别等于实际请求路径、实际 HTTP 方法与该端点允许的方法；任一字段缺失或取值不符都视为协议违规。

## 4. 操作类型

第 9.3 节的全部操作名如下。**v1 只冻结 `update_file_content` 的可执行行为**，其余取值在识别后返回 `OPERATION_NOT_SUPPORTED`，以避免在合并与目录展开规则冻结前产生跨端分歧。

| 操作 | v1 状态 | 备注 |
| --- | --- | --- |
| `create_file` | 已列名，未冻结可执行契约 | 需先冻结路径占用与初始版本规则。 |
| `update_file_content` | **已冻结** | 见第 5 节。 |
| `rename_file` | 已列名，未冻结可执行契约 | `file_id` 保持不变。 |
| `move_file` | 已列名，未冻结可执行契约 | `file_id` 保持不变。 |
| `delete_file` | 已列名，未冻结可执行契约 | 第 9.7 节软删除。 |
| `restore_file` | 已列名，未冻结可执行契约 | 使用原始 `file_id` 和新 revision。 |
| `create_directory` | 已列名，未冻结可执行契约 | |
| `rename_directory` | 已列名，未冻结可执行契约 | 服务端同事务更新后代路径。 |
| `move_directory` | 已列名，未冻结可执行契约 | |
| `delete_directory` | 已列名，未冻结可执行契约 | |
| `restore_directory` | 已列名，未冻结可执行契约 | |
| `set_file_metadata` | 已列名，未冻结可执行契约 | |

## 5. 提交判定顺序

提交按以下顺序执行。顺序本身是协议的一部分：**幂等查询先于文件基准校验**，因此旧基准上的重放不会返回冲突。

| # | 步骤 | 失败返回 |
| --- | --- | --- |
| 1 | 校验端点路径与 HTTP 方法；校验 `vault_id`、`device_id` **必填且为非空字符串**；二者都合法后再比较路由与请求体 `vault_id` 是否一致 | `ENDPOINT_NOT_FOUND`、`METHOD_NOT_ALLOWED`、`INVALID_REQUEST`（标识缺失或类型错误）、`VAULT_MISMATCH`（取值不一致） |
| 2 | 校验全部字段的类型与取值（含 `operation` 的类型、标识字段非空字符串、`path` 规范化、`content_hash` 格式、`client_timestamp` 的 RFC 3339 UTC 形式与日期时刻取值、`metadata` 为对象且含合法 `format`、`base_revision` 范围、基准字段类型与至少一项非 `null`） | `INVALID_REQUEST`、`BASE_REQUIRED` |
| 3 | 校验 `operation` 为已知操作名且本轮可执行 | `OPERATION_NOT_SUPPORTED` |
| 4 | 校验 `Idempotency-Key` 与 `operation_id` 一致（若提供） | `IDEMPOTENCY_KEY_MISMATCH` |
| 5 | **幂等账本查询**：命中则原样返回首次业务结果。账本既包含本进程内成功提交，也包含 `initial_state.idempotency` 声明的历史操作 | 成功（`replayed: true`）；同一 `operation_id` 不同内容（指纹不一致）返回 `IDEMPOTENCY_KEY_REUSED` |
| 6 | 定位目标文件 `vault_id` + `file_id` | `FILE_NOT_FOUND` |
| 7 | 校验 `path` 等于目标文件当前路径、`metadata.format` 等于文件格式 | `PATH_MISMATCH`、`FORMAT_MISMATCH` |
| 8 | **目标文件基准校验**：`base_version_id` / `base_content_hash` 与当前版本比对，两项都提供时必须同时匹配 | `FILE_VERSION_CONFLICT` |
| 9 | 校验上传会话已完成 | `UPLOAD_NOT_READY` |
| 10 | **内容校验**：实际字节数等于请求 `content_size`，实际字节 SHA-256 等于请求 `content_hash`，**且 completed 上传会话记录的 `content_size` / `content_hash` 与请求、实际字节三方一致** | `CONTENT_SIZE_MISMATCH`、`CONTENT_HASH_MISMATCH` |
| 11 | 提交状态变化：写 Blob（内容寻址，已存在则复用）→ 写新版本（记录父版本与 Blob）→ 更新文件当前指针 → 写 Change → `vault_revision + 1` | — |

要点：

- 第 1 步**先判「有无」再判「是否一致」**：`vault_id` / `device_id` 缺失或类型错误是 `INVALID_REQUEST`，只有二者都存在且合法、但 `vault_id` 取值与路由不同才是 `VAULT_MISMATCH`。这样客户端不会把「漏传字段」误读成「Vault 选错」。
- **第 2 步必须先于第 3 步**，顺序是协议的一部分。`operation: "frobnicate_file"` 与 `content_hash: "md5:abc"` 同时出现时返回 `INVALID_REQUEST`，而不是 `OPERATION_NOT_SUPPORTED`；只有当其余字段全部合法时，未知或未冻结的 `operation` 才返回 `OPERATION_NOT_SUPPORTED`。
- 第 8 步**只看目标文件**。其他文件推进了 `vault_revision` 不影响本次提交；`base_revision` 落后不构成冲突。
- 第 8 步对**两项基准**是「provided ⇒ must match」：只给 `base_version_id` 时只核对版本，只给 `base_content_hash` 时只核对哈希；两项都给出则**任一项不匹配即冲突**。因此「版本匹配但哈希过旧」和「哈希匹配但版本过旧」都必须返回 `FILE_VERSION_CONFLICT`。
- 一次有效内容更新恰好产生**一个新版本**和**一条 Change**，并把文件当前版本指针指向新版本。
- 第 10 步是**三方核对**，不是两方核对：请求声明的 `content_size` / `content_hash`、`ctx.resolveUpload` 实际取回的字节、以及 completed 上传会话里记录的 `content_size` / `content_hash` 必须完全一致。已完成会话本身就是一份内容指纹声明，只比对「请求 ↔ 实际字节」会让被篡改的会话静默通过，账本里就会留下无法追责的首次结果。会话指纹不符时返回稳定的 `CONTENT_SIZE_MISMATCH` / `CONTENT_HASH_MISMATCH`（大小先于哈希），并在错误体里同时给出 `upload_content_size` / `upload_content_hash`。
- 第 11 步是单个事务：任何一项失败都不留下新版本、新 Change 或推进后的 `vault_revision`。
- 幂等指纹覆盖**整个请求体**并写入账本参与状态比较。判重不能只看 `operation_id` 是否存在，也不能在重放路径上忽略指纹——否则「命中即返回」会掩盖「同一 ID 被用于另一份内容」。
- 新版本标识必须在 Vault 内未被占用；新 Blob 只在**完整**哈希相同时复用，且复用前核对已有记录的大小与标识自洽；上传会话按 `vault_id` + `blob_reference` 查找。
- **已删除文件上的 `update_file_content`**：v1 采用软删除语义，成功的内容更新**恢复**该文件（`is_deleted` 恢复为 `false`），并写入一条 `update_file_content` Change。写入后必须一致：最后一条 Change 的 `operation` 为 `update_file_content`、文件的 `is_deleted` 为 `false`、当前指针指向新版本、版本 metadata 与请求一致。任何成功写入都必须能通过 `validateInitialState`；不允许出现「返回 200 但 `is_deleted` 仍为 `true`」而最后一条 Change 却是 `update_file_content` 的自相矛盾状态。基准校验仍按该文件当前版本进行（软删除不改变 `current_version_id`）。

### 5.2 幂等与 `request_id` 取值规则

- 幂等键是 `operation_id`（可选再用 `Idempotency-Key` 显式声明，值必须相同）。
- 命中幂等账本时，返回**首次业务结果**的全部业务字段：`version_id`、`parent_version_id`、`change_id`、`blob_id`、`content_hash`、`content_size`、`vault_revision`、`file_id`、`path`、`operation_id`、`device_id`。
- `request_id` 每次请求重新分配；首次值通过 `original_request_id` 暴露。这样既保留追踪能力，又让业务结果逐项稳定。
- `replayed` 在首次响应为 `false`，重放响应为 `true`；它属于追踪字段，不参与业务结果比较。
- 重放**不新增** Blob、版本、Change，**不改变**文件当前指针，**不推进** `vault_revision`。
- 同一 `operation_id` 携带不同请求内容时返回 `IDEMPOTENCY_KEY_REUSED`，避免把两个不同意图混为一次操作。判定依据是**请求体指纹**：同一 `operation_id` 的指纹不一致即拒绝。
- **`operation_id` 在 Vault 内全局唯一**，与操作类型无关。历史 Change 中的**全部** `operation_id`（不只 `update_file_content`，也包括 `create_file` 等）在加载时都会进入「已占用」账本：有完整首次请求的可以重放；没有可重放首次结果的（历史 Change 缺首次请求，或由 `reserved_operation_ids` 显式声明）仍然**必须拒绝**新的不同操作，返回 `IDEMPOTENCY_KEY_REUSED`，`change_id` 回指占用该 ID 的 Change（`reserved_operation_ids` 来源为 `null`），`replayable` 为 `false`，且**不得新增第二条 Change**。因此「只为内容更新建账本」是不够的：换个操作类型复用同一个 ID 同样是错误。
- 幂等账本不是从空开始。`initial_state.idempotency` 显式携带历史操作的指纹、首次请求 ID、首次请求本身与结果；加载时做**完整交叉核对**：
  1. `fingerprint` 必须等于用 `request.body` 重新算出的稳定指纹；`request.method` 必须为 `POST`，`request.endpoint` 必须指向本 Vault 的 `sync/changes`，`request.headers` 里的 `Idempotency-Key`（若有）必须等于账本键。
  2. `request.body.operation_id` 必须等于账本键，`request.body.mode` 必须为 `submit`。
  3. **历史 Change ↔ 版本**：`version_id` 必须存在且属于**同一** `file_id`，`vault_revision` / `content_hash` / `content_size` / 父版本（`parent_version_id` ↔ 版本的 `base_version_id`）必须逐项一致；Change 的 `path` 必须规范化、`operation` 必须在第 9.3 节枚举内、`device_id` 与 `client_timestamp` 必须与版本的创建设备 / `created_at` 一致。
  4. **首次请求 ↔ 历史版本与 Change**：`vault_id`、`file_id`、`path`、`operation`、`content_hash`、`content_size`、`device_id`、`client_timestamp`、`metadata.format`、`base_version_id`（等于版本的父版本）、`base_content_hash`（等于父版本的完整哈希）、`base_revision`（`<= N-1`，即不超过首次写入 revision 之前的状态）必须逐项一致。
  5. **账本结果 ↔ 历史 Change 与版本**：`change_id`、`version_id`、`file_id`、`path`、`vault_revision`、`content_hash`、`content_size`、`parent_version_id`、`operation_id`、`device_id`、`vault_id`、`blob_id` 必须逐项一致，`mode` 为 `submit`、`replayed` 为 `false`、`protocol_version` 为 `sync-v1`，结果的 `request_id` 必须等于首次 `request_id`。

  任一不符都视为初态不自洽，建库即失败。因此**改动历史 Change 或首次请求后即使重算指纹也必须失败**——指纹只是第 1 条，第 3–5 条不依赖指纹。因此对历史 `operation_id` 的重放命中的是**首次结果**，而不是被当作新操作再写一条 Change；也不可能出现「账本对得上、请求却是另一份内容」的错位。连续多次重放都必须逐次稳定，状态快照会把指纹一并比较，重放路径上任何指纹丢失或改写都会被 `expect_state_unchanged` 发现。

对应夹具：[`duplicate-request.json`](../tests/sync-fixtures/duplicate-request.json)（`first-submit` → `replay-identical-request` → `replay-identical-request-again`，其中 `expect_replay_of_step` 与 `expect_state_unchanged` 逐项比较重放前后的 Blob、版本、Change、当前指针、`vault_revision` 与幂等账本指纹）。

历史操作的重放与拒绝由 [`stale-cursor-recovery.json`](../tests/sync-fixtures/stale-cursor-recovery.json) 覆盖：`op_roadmap_v2_0001` 在 revision 5 已成功写入 `ver_alpha_02` / `chg_000005`，`replay-historical-operation` 原样重放必须返回该首次结果且不新增任何记录；`reuse-historical-operation-different-content` 复用同一 ID 但改动 `client_timestamp`，必须返回 `IDEMPOTENCY_KEY_REUSED` 并回指 `req_000001`。

## 6. 错误结构

错误响应包含 `protocol_version`、`request_id`、稳定的 `code`、可读的 `message`，定位字段 `endpoint` / `method` / `allowed_method`，以及恢复所需字段。**定位字段在所有错误上都必须存在**（`404 ENDPOINT_NOT_FOUND`、`405 METHOD_NOT_ALLOWED`、各类业务错误一律如此），破坏其中任一项都必须让契约测试失败。

```json
{
  "protocol_version": "sync-v1",
  "request_id": "req_000002",
  "code": "FILE_VERSION_CONFLICT",
  "message": "目标文件已被修改，提交基准落后于服务端当前版本。",
  "file_id": "file_settings",
  "path": "data/settings.json",
  "base_version_id": "ver_settings_01",
  "base_content_hash": "sha256:21c9…aa73",
  "current_version_id": "ver_settings_02",
  "current_content_hash": "sha256:93eb…52b4",
  "current_content_size": 220,
  "current_blob_id": "blob_93ebd40144b3c07fa3e3da5336efdc92fbf276791700249011b923363ad552b4",
  "conflict_resolution": "fetch_current_version_then_three_way_merge",
  "endpoint": "/api/v1/vaults/vault_demo_0001/sync/changes",
  "method": "POST",
  "allowed_method": "POST"
```

### 6.1 错误码表
| `code` | HTTP | 触发条件 | 恢复字段 |
| --- | --- | --- | --- |
| `ENDPOINT_NOT_FOUND` | 404 | 端点路径不属于本轮协议 | `endpoint`、`method`、`allowed_method`（为 `null`） |
| `METHOD_NOT_ALLOWED` | 405 | 路径存在但方法与契约不符（`sync/changes` 非 `POST`，`sync/manifest` 非 `GET`） | `endpoint`、`method`、`allowed_method`（三者都必须出现，`allowed_method` 给出该路径唯一合法取值） |
| `VAULT_MISMATCH` | 400 / 404 | 路由与请求体 `vault_id` **取值**不一致（400），或路由 Vault 不属于该设备（404）。**标识缺失或类型错误不走本码**，而是 `INVALID_REQUEST`。 | `vault_id`、`expected_vault_id`（必须出现，值为服务端当前 Vault） |
| `MODE_REQUIRED` | 400 | `sync/changes` 的 `mode` 不是 `submit` / `pull` | `requested_mode`（错误响应不携带业务字段 `mode`） |
| `INVALID_REQUEST` | 400 | 缺字段（含 `vault_id` / `device_id` 缺失）、类型错误（含 `vault_id` / `device_id` / `operation_id` / `file_id` / `blob_reference` / `operation` 非非空字符串）、`path` 未规范化、`content_hash` 格式错误、`base_revision` 越界、`client_timestamp` 非 RFC 3339 UTC 或日期时刻取值越界、`metadata` 非对象或缺必填 `format`、`metadata.format` / `metadata.line_ending` 越界、基准字段类型错误 | `missing_fields` 或对应字段 |

| `IDEMPOTENCY_KEY_MISMATCH` | 400 | `Idempotency-Key` 与 `operation_id` 不一致 | `idempotency_key`、`operation_id` |
| `IDEMPOTENCY_KEY_REUSED` | 409 | 同一 `operation_id` 用于不同请求内容，或该 ID 已被历史 Change / `reserved_operation_ids` 占用 | 见 6.4 |
| `FILE_NOT_FOUND` | 404 | `file_id` 在 Vault 内不存在 | `file_id` |
| `PATH_MISMATCH` | 400 | 内容更新的 `path` 与文件当前路径不同 | `path`、`current_path` |
| `FORMAT_MISMATCH` | 400 | `metadata.format` 与文件格式不同 | `format`、`current_format` |
| `FILE_VERSION_CONFLICT` | 409 | 目标文件基准过旧 | 见 6.2 |
| `UPLOAD_NOT_READY` | 409 | `blob_reference` 无已完成上传 | `blob_reference` |

| `CONTENT_HASH_MISMATCH` | 409 | 请求 `content_hash`、实际字节 SHA-256、completed 上传会话记录的 `content_hash` 三者不一致 | `content_hash`、`actual_content_hash`、`upload_content_hash` |
| `CURSOR_TOO_OLD` | 409 | `last_server_revision < min_available_revision` | 见 6.3 |
| `REQUEST_ID_EXHAUSTED` | 503 | 下一个 `request_id` 序号超出可表示范围 `1..999999`（`req_` 加六位数字） | `request_id`（为 `null`）；此时不会生成七位标识，也不改变协议状态 |
| `REVISION_EXHAUSTED` | 503 | `vault_revision` 已达可安全表示的整数上界 `Number.MAX_SAFE_INTEGER`，无法再安全分配新 revision | `vault_revision`、`max_safe_revision`；此时不分配新 revision，也不改变协议状态 |

### 6.1.1 `VAULT_MISMATCH`

`VAULT_MISMATCH` **必须**同时给出请求携带的 `vault_id` 与服务端期望的 `expected_vault_id`，客户端据此判断是选错了 Vault 还是漏传/传错字段：

```json
{
  "protocol_version": "sync-v1",
  "request_id": "req_000004",
  "code": "VAULT_MISMATCH",
  "message": "请求体 vault_id 与路由不一致。",
  "vault_id": "vault_other_9999",
  "expected_vault_id": "vault_demo_0001",
  "endpoint": "/api/v1/vaults/vault_demo_0001/sync/changes",
  "method": "POST",
  "allowed_method": "POST"
}
```

- 请求体 `vault_id` 与路由不一致 → HTTP `400`，`vault_id` 为请求体取值，`expected_vault_id` 为服务端当前 Vault。
- 路由 `vault_id` 不属于该设备 → HTTP `404`，`vault_id` 为路由取值，`expected_vault_id` 同样指向服务端当前 Vault。
- **`vault_id` / `device_id` 缺失或类型错误不是本码**，而是 `INVALID_REQUEST` 并在 `missing_fields` 中列出缺失项。

对应夹具：[`file-base-too-old.json`](../tests/sync-fixtures/file-base-too-old.json) 的 `vault-mismatch-expected-vault-id`（带 `expect_error_fields`，断言 `vault_id` 与 `expected_vault_id` 同时出现）；测试用例「VAULT_MISMATCH 错误结构包含 expected_vault_id…」另外覆盖路由 404 分支与「缺失标识不被误报」。

### 6.2 `FILE_VERSION_CONFLICT`

恢复字段如下（每一项都必须出现；未提供的请求基准显式为 `null`）：

| 字段 | 含义 |
| --- | --- |
| `file_id` | 冲突的目标文件身份。 |
| `path` | 目标文件的当前路径。 |
| `base_version_id` | 请求携带的基准版本，未提供时为 `null`。 |
| `base_content_hash` | 请求携带的基准哈希，未提供时为 `null`。 |
| `current_version_id` | 服务端当前版本，客户端用它定位远端内容。 |
| `current_content_hash` | 服务端当前版本的完整内容 SHA-256。 |
| `current_content_size` | 服务端当前版本的字节数。 |
| `current_blob_id` | 服务端当前版本引用的 Blob。 |
| `conflict_resolution` | 固定 `fetch_current_version_then_three_way_merge`，提示后续处理方向。 |

客户端用这些字段定位远端内容，交给后续三方合并。

判定对两项基准是**逐项「provided ⇒ must match」且取或**：

| 请求携带的基准 | 触发冲突的条件 |
| --- | --- |
| 仅 `base_version_id` | `base_version_id != current_version_id` |
| 仅 `base_content_hash` | `base_content_hash != current_content_hash` |
| 两项都带 | `base_version_id != current_version_id` **或** `base_content_hash != current_content_hash` |

因此下列两种「只错一项」的请求同样是冲突，都必须返回 `FILE_VERSION_CONFLICT`：

- **版本匹配、哈希不匹配**：`base_version_id == current_version_id` 但 `base_content_hash` 是更早版本的哈希。
- **哈希匹配、版本不匹配**：`base_content_hash == current_content_hash` 但 `base_version_id` 已被取代。

这两种情形说明提交方对目标文件的「身份」和「内容」认知至少有一项落后，不能仅凭另一项匹配放行。

冲突提交的副作用边界：

- 保留远端当前版本与当前指针（不变）。
- **不**新增版本、**不**新增 Change、**不**推进 `vault_revision`、**不**新增 Blob，也**不**写入幂等账本。
- 本地候选内容只留在客户端，服务端不接受；客户端可另存冲突文件后再合并（第 9.6 节）。

对应夹具：[`file-base-too-old.json`](../tests/sync-fixtures/file-base-too-old.json)。其中 `remote-advances-settings` 先推进目标 JSON 文件，随后三步分别覆盖三种冲突方向：

| 步骤 | 基准情形 |
| --- | --- |
| `stale-local-json-rejected` | 版本与哈希都过旧 |
| `version-matches-hash-stale-rejected` | `base_version_id` 匹配、`base_content_hash` 过旧 |
| `hash-matches-version-stale-rejected` | `base_content_hash` 匹配、`base_version_id` 过旧 |

三步都带 `expect_conflict_locates_remote`，用错误中的当前版本在服务端定位远端内容并与 `content/data/settings-v2.json` 的真实字节比对；都带 `expect_state_unchanged`，逐项比较冲突前后的指针、版本数、Change 数和 `vault_revision`。测试用例「冲突判定必须同时校验 base_version_id 与 base_content_hash」会先断言每一步「版本匹配 / 哈希匹配」的期望值与服务端实际状态一致，因此破坏 `versionMatches` 或 `hashMatches` 中任意一个都必然失败。

> JSON 样本按**原始字节**计算 SHA-256，不经过解析后重新序列化，因此测试会先解析校验 JSON 合法性，再对原始字节求哈希。

**续拉游标必须来自 manifest 响应，不能硬编码。** 夹具中 `resume-from-snapshot-revision` 用 `cursor_from_step` / `cursor_from_field` 声明游标来源，请求体里**刻意不写** `last_server_revision`：

```json
{
  "id": "resume-from-snapshot-revision",
  "cursor_from_step": 3,
  "cursor_from_field": "snapshot_revision",
  "request": { "body": { "mode": "pull", "vault_id": "vault_demo_0001", "device_id": "device_mac_0001" } }
}
```

测试执行到该步时会**用上一步响应的 `snapshot_revision` 注入**请求的 `last_server_revision`（缺失则 `INVALID_REQUEST`，所以硬编码无处可藏），并断言：来源步骤确实是 manifest、来源值是合法的非负整数、执行器确实做了注入而不是读夹具里的字面量。因此：

- 夹具里出现 `last_server_revision` 字面量会被「绑定步骤不得硬编码」断言拦下；
- 所有步骤（绑定与未绑定）都经过**同一个请求构造函数**。绑定步骤的游标由 manifest 响应派生，未绑定步骤原样使用夹具请求；不存在「另一条绕过注入的独立构造路径」。
- 场景内先后在 revision 6 与 7 上各取一次 manifest 并各自续拉：游标 6 应返回 `chg_000007`，游标 7 应返回空数组。只要执行器把派生值写死为 `6`，第二次续拉就会多返回 `chg_000007`，用例「续拉游标跟随快照 revision 变化，硬编码 6 必然失败」随即失败。
- 对照实验在**同一份含历史 Change 的最终状态**上进行：写死 6 会返回 `['chg_000007']`，而按实际游标 7 续拉返回 `[]`，两者必须不同。

| --- | --- |
| `idempotency` | **历史操作的幂等账本**。每项包含 `operation_id`、`fingerprint`（首次请求体的稳定指纹）、`request_id`（首次请求 ID）、`request`（首次请求，供重放）与 `result`（首次业务结果）。加载器做三方交叉核对：① `fingerprint` 必须等于用 `request.body` 重算的指纹；② `request.body.operation_id` 必须等于账本键、`mode` 必须为 `submit`；③ `result` 与 `request.body` 都必须与历史 Change 逐项一致，覆盖 `change_id`、`version_id`、`file_id`、`path`、`vault_revision`、`content_hash`、`content_size`、父版本、设备与 `client_timestamp`。历史 `update_file_content` 缺少账本条目视为初态不自洽。这样「历史 operation_id 重放」才会命中幂等而不是重复写入。 |
| `version_samples` | **场景顶层字段**（与 `initial_state`、`steps` 同级）：`version_id -> content/ 相对路径` 的映射，声明每个初始版本对应的正文样本。测试会读取样本原始字节，逐项核对 `content_size`、该版本引用的 Blob，以及**完整** SHA-256。给样本多加一个空格也必须被发现。 |
| `reserved_operation_ids` | **已占用但无完整历史请求**的 `operation_id` 列表。用于表达「这个 ID 在服务端确实用过（例如提交失败后重试换 ID），但没有可重放的首次结果」。这些 ID 不得与 `idempotency` 的键或历史 Change 的 `operation_id` 重复。新请求复用它们必须返回 `IDEMPOTENCY_KEY_REUSED`（`change_id: null`、`replayable: false`）。 |
| `request_sequence` | 可选的、下一个可用的 `request_id` 序号（正序遍历 `req_000001` 起）。**可用范围是 `1..999999`**：`request_id` 是 `req_` 加**恰好**六位数字，序号一旦超过 `999999` 就只能生成七位的 `req_1000000`，直接违反格式。显式声明超出范围、或历史已用到 `999999` 导致缺省推导越界，都属于初态不自洽，加载阶段即拒绝。**若缺省则由历史推导**：取 `idempotency[].request_id` 与 `request_log[].request_id` 里的最大序号 + 1。显式声明时若小于等于历史已用序号，同样属于初态不自洽。这样删掉该字段也不会让新请求重用历史 `request_id`，而运行期序号用尽时返回 `REQUEST_ID_EXHAUSTED`，绝不静默产出七位标识。 |
| `request_log` | 可选的、历史已发出的请求跟踪标识列表（`[{ "request_id": "req_…" }]`）。只参与 `request_id` 唯一性与序号推导，不参与协议状态比较。 |

`initial_state` 的其它硬约束：

- `min_available_revision` **只有缺省才等于 `0`**；显式 `null`、`undefined`、负数、小数或非整数都视为不自洽，加载阶段即拒绝（`?? 0` 的默认值语义只对「键不存在」生效）。
- `versions[].vault_revision`、`changes[].vault_revision` 都不得超过 `vault_revision`，且 `changes` 必须按 revision 严格递增。
- **revision 连续性**：从 `min_available_revision + 1` 到 `vault_revision` 的每个 revision 都必须有对应 Change。`min_available_revision` 及更早的历史允许已压缩而缺失（包括等于下界的创建 Change）。缺失任何中间 revision 即视为不自洽。**校验必须按实际保留的 Change revision 排序检查首个 / 中间 / 尾部缺口**，复杂度只与记录数线性相关；绝不能从 `min_available_revision` 逐个 `+1` 循环到 `vault_revision`，否则一个巨大的 `vault_revision` 就能把加载校验拖死。
- **集合字段语义一致**：`files`、`versions`、`blobs`、`changes`、`upload_sessions`、`idempotency`、`request_log`、`reserved_operation_ids` 缺省时都视为空集合，显式出现时必须是数组。验证器与建库函数共用这套语义，因此「`validateInitialState` 通过」必然意味着 `createVaultState` 能建库；`files: {}` 之类显式错误类型仍会被拒绝。
- **版本图**：`versions[].base_version_id` 指向的父版本必须存在、属于**同一** `file_id`，且其 `vault_revision` **严格早于**子版本；父链不得成环。同一文件里出现未来父版本或环，都属于不自洽。
- **可证明的当前指针链**：按同一文件的保留 Change revision 顺序重建「可证明的当前版本」，并要求每个**产生版本**的 Change 的 `parent_version_id` 等于当时可证明的当前版本（首个保留 Change 允许父版本落在压缩下界以内，以容纳压缩边界）。把父引用改回更早版本（基准回退）或改成 `null` 都属于不自洽：这样的历史等于「在更早的基准上覆盖写入」，重放得到的结果会与服务端不同。
- **不得引用未来版本**：任何 Change（含 `delete_file` / `delete_directory` 等**复用**版本的 Change）引用的 `version.vault_revision` 都不得晚于该 Change 的 `vault_revision`。删除必须引用当时已经存在的版本，删除后的 update 也必须以删除前的当前版本为父版本。
- **保留区间内的版本 ↔ Change 双向绑定**：`revision >= min_available_revision + 1` 的每个版本，必须恰好有一条**同 revision 且产生该版本**的 Change 指向它（`create_file` / `update_file_content` / `restore_file`）。同 revision 的孤立额外版本、缺少对应 Change 的保留版本都必须被拒绝。
- **`change_id` 全局唯一**：历史 `change_id` 不得重复；新生成的 `change_id` 默认取 `chg_<revision>`，若该标识已被占用（例如迁移导入的旧数据），必须追加后缀避开，绝不与历史冲突。
- `upload_sessions[].status` 必须是 `pending` / `completed` / `failed` 之一；只有 `completed` 可用于提交。跨 Vault 的上传会话与 Blob 在加载阶段即被拒绝。**上传会话必须携带可留存的原始内容指纹**：`content_hash`（完整 `sha256:`）与 `content_size` 必填，`blob_id`（若出现）必须等于按完整哈希生成的标识。首次请求的 `blob_reference` 必须能在 `upload_sessions` 中找到，且其 `content_hash` / `content_size` 必须与请求一致；换成同一夹具里另一个有效样本也会在加载阶段失败。**运行期同样要核对**：提交时 completed 会话记录的 `content_hash` / `content_size` 必须与请求、实际取回字节三方一致，任一方不一致都返回稳定的 `CONTENT_HASH_MISMATCH` / `CONTENT_SIZE_MISMATCH`，且不写入 Blob、版本、Change、幂等账本，也不推进 `vault_revision`。**同一完整内容哈希只能对应一个 `content_size`**：初态里 completed 会话、它引用的 Blob、以及所有同哈希 Blob 的大小必须互相一致，同哈希不同大小的初态直接拒绝。运行期复用已有 Blob 而记录大小不符时，`CONTENT_SIZE_MISMATCH` 必须同时给出 `upload_content_size`（上传会话声明的大小）与 `blob_content_size`（Blob 记录的大小），否则客户端无法判断该修哪一侧。
- **文件字段**：`files[].path` 必须是第 3.1 节口径下的规范化 Vault 相对路径（禁止 `..`、`.`、空段、前导 `/`、反斜杠、NUL，且不得与其它文件重复）；`files[].format` 必须属于 `md` / `txt` / `json`；`file_id` 必须是非空字符串，`current_version_id` 必须显式出现（字符串或 `null`），`is_deleted`（若出现）必须是布尔值。`../bad`、`.`、`rtf` 之类取值都会让加载失败。
- **文件当前指针**：`files[].current_version_id` 必须等于该文件**保留历史可证明的最终版本**。有保留 Change 时，它是该文件 revision 最大的那条 Change 指向的版本；该文件的 Change 已被压缩（全部 `<= min_available_revision`）时，指针必须指向初始快照里该文件 revision 最大的版本，且该 revision 不得晚于下界——**不能因为缺少保留 Change 就强制 `current_version_id = null`**。`is_deleted` 必须与最后一个**保留**Change 的操作类型一致（`delete_file` / `delete_directory` 为 `true`，其它为 `false`）；没有保留删除 Change 的文件必须为 `false`。文件 `format` 必须与最终版本的 `metadata.format` 一致。把指针换回更早的版本、或让 `is_deleted` 与历史相反，都属于不自洽。
- **历史 Change 与路径 / 版本绑定**：`changes[].path` 必须等于对应 `files[].path`；`changes[].created_at`、`changes[].vault_id`、`changes[].version_id`、`changes[].parent_version_id`（可为 `null`，但必须显式出现）、`content_hash`、`content_size` 都必须存在且类型 / 值域正确。
- **历史版本的来源字段（逐版本核对，不只当前指针版本）**：凡是有**产生该版本的操作**（`create_file` / `update_file_content` / `restore_file`）的 Change 对应的历史版本——**包括不是文件当前 `current_version_id` 的中间版本**——`created_by_device_id`、`created_at` 与 `metadata` 都必须存在。
  - `created_by_device_id` / `created_at` 分别等于**该版本对应 Change** 的 `device_id` / `client_timestamp`；`created_at` 还必须是合法的 RFC 3339 UTC。
  - `metadata.format` 必填、在枚举内，**且等于所属 `files[].format`**；若该写入操作在 `idempotency` 里有可追溯的首次请求，还必须等于该请求的 `metadata.format`。
  - `metadata.line_ending` 的**存在性**与取值必须与首次请求一致：请求提供了就必须有且相同，请求未提供时版本也不得凭空出现。
  - 删除任一项、改动 `metadata.format`（即使改成另一个合法枚举值）、或单方增删 `line_ending`，都视为不自洽（不能只在字段存在时才比较，也不能只检查文件当前指针指向的那个版本）。
  - **压缩语义不受影响**：没有任何可追溯 Change 的版本（`revision <= min_available_revision` 且创建事件已被压缩）不要求 `created_by_device_id` / `created_at` / `metadata` 与请求逐项一致，但仍要求其 `metadata.format`（若出现）与所属文件格式一致。`compressed-history-recovery` 的 `ver_notes_02` 就属于这一类，必须继续加载成功。
- **首次请求完整校验**：`idempotency[].request.body` 必须是**完整且合法**的提交请求 —— `mode` 为 `submit`；`vault_id`、`device_id`、`operation_id`、`file_id`、`operation`、`path`（规范化）、`blob_reference`、`content_hash`（`sha256:<64 位小写十六进制>`）都是非空字符串或合法取值；`content_size` 是非负整数；`client_timestamp` 是 RFC 3339 UTC；`metadata` 是对象且 `format` 在枚举内、`line_ending`（若出现）在枚举内；`base_revision` 是非负整数且 **`<= N-1`**（写入前状态）；**基准字段至少提供一项**且类型正确。
  - **单哈希基准**：只提供 `base_content_hash`（不带 `base_version_id`）是在线提交允许的形式，历史加载必须接受它；只给正确的 `base_content_hash` 时，重放仍必须命中首次结果。两项都提供时必须**同时匹配**。只给错误的哈希、或错误的 `base_version_id`，都必须在加载阶段失败。
  - **可重放性**：`operation` 必须是本模型可执行的操作（v1 只有 `update_file_content`）。历史记录可以包含未来操作，但这样的记录不能进入可重放账本——否则首次结果会先撞上 `OPERATION_NOT_SUPPORTED`（400）。
  - **路由与 query**：`request.method` 必须为 `POST`、`request.endpoint` 必须是本 Vault 的 `sync/changes`；`request.query.vault_id`（若出现）必须与本 Vault 一致，否则重放会返回 404。历史请求也可能只保存完整 `request.url`：其中的查询串必须用与运行时**相同的 `URLSearchParams`** 解析，`vault_id` 同样必须与本 Vault 一致（`query` 与 `url` 同时出现时必须都一致），不能因为只查 `query` 对象而让 URL 查询串绕过加载校验。
  - **`Idempotency-Key` 是可选的**：首次请求与重放都可以完全省略该头。若出现，必须**大小写无关地**等于 `operation_id`；省略时 `operation_id` 仍是幂等键，历史请求必须通过加载并原样重放命中首次结果。
  - **可留存内容**：`request.blob_reference` 必须对应一个 `completed` 的上传样本，且样本的 `content_hash` / `content_size` 与请求一致；历史版本的 `blob_id` 必须等于按完整内容哈希生成的标识。换成同一夹具里另一个有效样本，即使重算指纹也必须在 `validateInitialState` 阶段失败。
  - 缺 `blob_reference`、把 `line_ending` 改成 `bogus` 这类破坏即使重算指纹也必须在**加载阶段**被发现，而不是等到重放才返回 `INVALID_REQUEST`。通过校验后，原样重放必须返回 200、`replayed: true` 与首次业务结果。
- **`reserved_operation_ids` 不得与历史重复**：其中的每个 ID 都不得等于任何历史 `changes[].operation_id`，也不得等于 `idempotency` 的键。否则该 ID 同时主张「有首次结果」与「没有首次结果」，必须拒绝。

标识生成同样受约束：版本标识必须避开 Vault 内已被占用的值（不能只用「该文件已有版本数 + 1」）；Blob 标识按**完整**哈希生成，复用前也按**完整**哈希匹配——只共享 12 位前缀的两份不同字节必须得到两个 Blob；上传会话按 `vault_id` + `blob_reference` 查找。初态若出现跨 Vault 的 Blob 或上传会话，加载阶段即失败。

**路由中的 Vault 段必须百分号解码**：标准 `Request` 的 `url.pathname` 对非 ASCII 的 Vault ID（例如 `vault_中文`）是百分号编码的，模型必须 `decodeURIComponent` 路径段后再与 `state.vault_id` 比较，否则标准 Request 永远访问不到这类 Vault。非法百分号编码（`%ZZ`、被截断的 `%E4`、解码后跨越段边界的 `%2F`）不是任何协议端点，返回稳定的 `ENDPOINT_NOT_FOUND`（404），**不得抛出未捕获异常**。响应里的 `endpoint` 仍回显**实际请求路径**（保留百分号编码），便于定位真实请求。

`scenario` 与文件名是**双向约束**：加载器要求 `scenario` 等于文件名去掉 `.json`，并要求所有场景名互不重复；任一条件不满足都会在测试启动阶段直接失败，而不是被索引静默覆盖。这样把 `submit-markdown.json` 改名或复制成第二个文件时，测试不会仍然通过。

### 8.4 断言指令语义

| 指令 | 语义 |
| --- | --- |
| `expected_status` | 必须返回的 HTTP 状态码。测试入口还会校验夹具自带的 `request.method` 与端点匹配（`changes` 为 `POST`、`manifest` 为 `GET`），夹具用错方法会直接失败。`expected_status >= 400` 的步骤必须在 `expected_result` 里给出**非空字符串** `code`：只断言「失败了」无法证明失败原因就是协议要求的那一条，加载阶段即拒绝。 |
| `expected_result` | **必需的响应证据**：响应体的深子集匹配（数组要求长度一致并逐元素匹配）。错误步骤同样必须给出它，并至少包含 `code`。 |
| `expected_state` | 对压平后的状态视图做点路径比较，例如 `files.file_roadmap.current_version_id`、`counts.changes`、`changes.1.change_id`。 |
| `expect_state_unchanged` | 请求前后协议状态必须逐项相同。快照覆盖 `vault_revision`、`min_available_revision`、文件（含当前指针与哈希/大小/Blob）、版本、Blob、Change、**上传会话**（`uploads`）、**已占用 `operation_id`**（`used_operations`）与幂等账本（含**指纹**）。因此「改坏上传会话」「丢弃已占用 ID」「拒绝请求却新增版本/Change/Blob/幂等记录」「失败分支推进 `vault_revision`」都会被本指令发现。请求跟踪计数器（`request_sequence` / 已发出 `request_id`）按设计每次请求都推进，不参与此比较，其唯一性由独立断言负责。 |
| `expect_replay_of_step` | 业务字段必须与指定步骤逐项相同，`replayed` 为 `true`，`original_request_id` 回指首次请求，且状态不变。 |
| `cursor_from_step` / `cursor_from_field` | 请求的 `last_server_revision` **不由夹具硬编码**，而是执行时从指定步骤响应（必须是 manifest）的 `snapshot_revision` 注入。绑定步骤在夹具里不得出现 `last_server_revision` 字面量，否则断言失败。 |
| `expect_error_fields` | **错误字段的附加断言**，不能替代状态证据：错误响应必须包含给定字段，且按声明值的类型比较（`null`、`false`、数字、数组、对象都按实际类型比对）。用于核对 `VAULT_MISMATCH` 的 `expected_vault_id`、`CURSOR_TOO_OLD` 的 `manifest_endpoint`、`REQUEST_ID_EXHAUSTED` 的 `request_id: null` 等恢复字段。 |
| `expect_conflict_locates_remote` | 用错误中的 `current_version_id` / `current_blob_id` 在服务端定位远端内容，并与指定样本的真实字节哈希比对。 |
| `expect_manifest_restores_map` | 用 manifest 条目重建文件映射，并与服务端状态逐项核对。 |
| （内建）manifest 的 `vault_id` 来源 | 所有 manifest 响应都断言 `vault_id` 等于路由中的 `{vault_id}`：GET 没有正文，查询参数只能用于 `device_id`，不能成为 Vault 的权威来源。 |
| （内建）错误定位字段 | 每个 `expected_status >= 400` 的步骤都断言 `endpoint`、`method` 存在且等于实际请求，`allowed_method` 存在且等于该端点唯一合法方法（端点不在协议内为 `null`）。破坏任一字段测试即失败。 |
| （内建）步骤证据 | 每一步必须有**两类证据**：① 响应证据 —— `expected_result` 是非空对象（`{}` 不算）；② 状态证据 —— 非空 `expected_state` 或 `expect_state_unchanged: true`。`expect_error_fields` 只是错误字段的附加断言，**不能**替代任何一类证据。 |
| （内建）历史原样重放 | `expect_historical_replay` 指向 `initial_state.idempotency` 的下标：该步必须逐项核对完整路由、`query.vault_id`、方法、endpoint、请求体与 `Idempotency-Key`，并断言 200、`replayed: true`、首次业务结果与状态不变。 |
| （内建）提交字段交叉断言 | 成功提交的新 Change 的 `operation_id`、`device_id`、`client_timestamp`、`operation`、`path`、`file_id`、`revision` 必须分别与请求、版本、文件一致。 |
| （内建）pull 成功响应完整校验 | 每个成功 pull 响应都必须满足：`vault_id` 等于夹具 `initial_state.vault_id`；`device_id` 等于**请求体** `device_id`；`from_revision` 回显请求 `last_server_revision`；`to_revision` 等于响应时刻服务端的 `vault_revision`；`min_available_revision` 等于服务端下界；`has_more` 为 `false`；`changes` 为数组、按 revision 严格递增且全部落在 `(from_revision, to_revision]`；每条 Change 逐项等于 `state.changes` 中对应记录。把响应改成错误 `vault_id` / `device_id`（或 `to_revision` / `has_more`）时执行器必然失败。 |

- 正常实现退出码为 `0`，输出中可辨认五个场景。
- 测试入口先做完整性前置检查：五个必需场景必须全部加载且 `scenario` 与文件名一致、场景名唯一，`.md` / `.txt` / `.json` 三种样本必须都存在且被场景引用，否则直接失败，避免夹具缺失或被改名导致空跑通过。
- **全部已加载场景都会被实际执行**（不只是五个固定名称）。「场景：…」主循环在真正跑过场景与每一步、且全部断言通过后，把执行记录写入统一的 `MAIN_LOOP_EXECUTION`。覆盖测试（「五个必需场景均已由主循环实际执行」「全部已加载场景都会由主循环实际执行」）**只读这份记录**，不自行补跑场景：把某个场景从主循环里摘掉、或在某个步骤提前 `break`，覆盖断言必然失败；新增夹具也不会因为没被登记而静默跳过。
- **每一步都必须同时具备响应证据与状态证据**：`expected_result` 是非空对象（响应证据），并且必须有非空 `expected_state` 或 `expect_state_unchanged: true`（状态证据）。加载阶段逐条校验，缺失即失败；`expect_error_fields` 只是错误字段的附加断言，不能替代任何一类证据。断言失败的步骤不得登记完成。
- **至少一个成功提交走异步上传**：`async_upload_steps` 声明以 `Promise<Buffer>` 解析上传正文的步骤，执行器真实 `await` 它。移除模型里的 `await` 会让对应测试失败。
- **初始版本必须与正文样本逐项对照**：`version_samples` 给出映射，测试比较完整 SHA-256、字节数与该版本引用的 Blob。仅给样本追加一个空格也会被发现。
- **历史幂等账本随初态加载**：账本条目与历史 Change 交叉核对。原请求重放必须返回首次结果且状态（含指纹）不变；同 ID 异内容必须返回 `IDEMPOTENCY_KEY_REUSED`。
- **manifest 用标准 `Request` 实际构造**：断言 `request.body === null`，并反向断言「给 GET 带 body 会在构造阶段抛 `TypeError`」。这是 Web 端能按契约取到 manifest 的直接证据。
- 字段类型与 `client_timestamp` 边界另由独立用例覆盖：`pull` / `manifest` 的 `device_id`、`vault_id` **缺失、`null`、空串或类型错误**都返回 `INVALID_REQUEST`，且不会被误报成 `VAULT_MISMATCH` / `CURSOR_TOO_OLD`；`file_id`、`blob_reference`、`operation` 类型错误在业务查找前返回 `INVALID_REQUEST`；`metadata` 为 `{}` 或缺 `format` 返回 `INVALID_REQUEST`；`2026-02-29T09:05:00Z`、`2026-04-31T09:05:00Z`、`2026-01-01T24:00:00Z` 等「形状合法但取值不存在」的时间戳返回 `INVALID_REQUEST`。
- **组合非法请求**由专门用例覆盖：未知 / 未冻结 `operation` 与非法 `content_hash`、非规范化 `path`、空 `metadata`、非法 `client_timestamp`、越界 `base_revision`、缺失标识等同时出现时，一律返回 `INVALID_REQUEST`（第 2 步先于第 3 步）；字段全部合法时未知 `operation` 仍返回 `OPERATION_NOT_SUPPORTED`，防止把顺序改成「永远报 `INVALID_REQUEST`」也能通过。
- **冲突两个方向**由专门用例覆盖：先断言每步「版本匹配 / 哈希匹配」的期望与前置状态一致，再断言 `FILE_VERSION_CONFLICT` 与状态无副作用。破坏 `versionMatches` 或 `hashMatches` 中任一个都会失败。
- **续拉游标**由 `cursor_from_step` 绑定：请求值来自 manifest 响应的 `snapshot_revision`，不是硬编码数字。绑定判据是「是否声明了 `cursor_from_step`」而不是取值真假，因此 `snapshot_revision` 恰好为 `0` 时也会正常注入。零游标场景（`vault_revision = 0` 的 Vault）走与其它场景**完全相同**的 `runScenario` → `buildRequest` → `handleRequest` → 步骤证据路径，并同时断言「绑定声明为 0」「请求体真的携带 0」「响应回显 0」；同一用例还用 `boundCursor || undefined` 复现真值判断的破坏，确认那样构造出的请求必然缺字段并被判 `INVALID_REQUEST`。
- **标准 `Request` 是唯一的请求构造方式**：场景执行时每一步都用 `buildRequest` 构造标准 `Request`（`POST` 序列化 JSON 正文、`GET` 无正文），被测模型读取 URL / headers / body 的路径与真实客户端一致。另有用例直接断言：同一个 `Request` 携带 JSON 正文时提交成功且业务结果与夹具期望逐项一致；空正文 `POST` 变成 `INVALID_REQUEST`；非法 JSON 返回 `body_error`；同一 `Request` 对象可复用（幂等重放命中）。
- 每个场景从 `initial_state` 起逐步执行请求，把每一步的实际状态传给下一步。状态转换只读取请求、样本和当前状态，`expected_result` / `expected_state` 仅供断言使用。
