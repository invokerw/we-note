# WeNote 开发工作流

本流程把用户需求落实为可追踪的开发账本、单任务记录和独立交付环境，适用于功能开发、Bug 修复、重构、测试、文档和工程维护。

## 任务分类

| 类型 | 适用范围 | 必要证据 |
| --- | --- | --- |
| `feature` | 新功能、接口或用户能力 | 新行为测试，必要时补充文档和端到端验收 |
| `bugfix` | 已确认的错误、回归或数据问题 | 能复现问题的失败测试，以及修复后的回归通过证据 |
| `refactor` | 保持行为不变的结构调整、性能或可维护性改进 | 受影响范围的回归测试和行为对照 |
| `test` | 测试夹具、测试基础设施或覆盖率改进 | 新增测试能够在目标入口执行 |
| `docs` | 产品、接口、开发或运维文档 | 链接、示例、命令和术语可验证 |
| `chore` | 构建、依赖、脚本、配置和其他工程维护 | 对应构建、静态检查或运行验证 |

需求同时涉及多个类型时，选择主要目标作为主类型，并在任务记录中列出其他影响面。

## 账本与任务记录

`docs/开发账本.md` 是任务索引和生命周期记录。每项任务使用稳定 ID，建议格式为 `<TYPE>-YYYYMMDD-<short-name>`，其中 `TYPE` 使用大写分类名，例如 `FEAT-20261123-share-assets` 或 `FIX-20261123-sync-cursor`。

任务开始时新增账本条目，并创建 `docs/tasks/<任务 ID>.md`。任务记录至少包含用户原始需求、问题或目标、范围、明确排除项、影响端、验收条件、测试命令、基线提交、分支、worktree、服务端和客户端交付方式。记录模板见 [任务记录模板](../.codex/skills/wenote-development/references/任务记录模板.md)。

任务记录按时间追加验证证据。每次验收记录实际命令、退出状态、关键输出、未验证项和下一步。不要用“已测试”替代命令和结果。

账本状态使用以下值。

| 状态 | 含义 |
| --- | --- |
| `PLANNED` | 已登记，尚未开始实现 |
| `IN_PROGRESS` | 正在任务 worktree 中开发 |
| `DELIVERED` | 自我验收通过，已交付用户验收 |
| `CHANGES_REQUESTED` | 用户验收后要求修改，继续使用原分支和 worktree |
| `ACCEPTED` | 用户确认验收通过，等待合并清理 |
| `MERGED` | 已合回基线分支并完成清理 |
| `BLOCKED` | 缺少需求决策、环境或外部依赖，阻塞原因必须写入任务记录 |
| `ABANDONED` | 用户明确放弃，保留原因和最后状态 |

## 新窗口开始开发

新窗口接到具体开发任务时，先检查当前分支、工作区和已有 worktree。确认基线分支和用户未提交的无关改动后，为任务生成稳定 ID。

```sh
git status --short --branch
git worktree list
git switch main
git worktree add -b codex/<type>-<short-name>-<yyyymmdd> ../we-note-<task-id> main
```

如果主工作区存在用户未提交的改动，保留它们，不把它们带入任务。若任务需要从其他基线开始，在任务记录中写明基线提交。

在新 worktree 中先更新账本和任务记录，再写实现代码。任务记录的基线提交、分支和 worktree 路径必须与 Git 实际状态一致。

## TDD 开发循环

采用红、绿、重构的循环。红阶段让测试准确暴露需求或 Bug，绿阶段用最小实现通过测试，重构阶段在全绿基础上整理结构并保持行为契约。

1. 阅读相关实现、既有测试、产品设计和接口文档，确认任务边界。
2. 把验收条件转成最小可执行测试。Bug 修复先加入回归测试，功能开发先覆盖成功路径和关键失败路径。
3. 运行聚焦测试并确认它因预期原因失败。把失败命令和输出摘要写入任务记录。
4. 编写能够让测试通过的最小实现，保持已有调用方的行为契约。
5. 重新运行聚焦测试，再运行受影响模块的回归测试。需要时补充跨端、协议、构建或端到端测试。
6. 在测试全绿后进行必要重构，再重复相关测试。运行 `git diff --check`，检查任务记录和账本也在交付范围内。

文档或配置任务可以使用链接检查、格式检查、构建和启动验证代替代码测试。无法自动化的验收项必须写出人工步骤和观察结果。

## 独立服务端验收

服务端改动必须从任务 worktree 启动独立实例。使用任务专用端口，避免占用主工作区的服务。仓库自带的本地入口从当前 worktree 构建网页和 API。

```sh
cd ../we-note-<task-id>
./scripts/local.py start --port <unique-port>
./scripts/local.py status
curl -fsS http://127.0.0.1:<unique-port>/healthz
```

服务端的构建产物、SQLite 数据、PID 和日志必须留在任务 worktree 对应的运行目录。交付时记录服务地址、PID、日志路径、测试账户或初始化步骤和停止命令。验收完成后先停止独立服务，再进入合并清理流程。

如果任务只修改服务端，可以交付独立服务地址和 API 验收命令。如果同时修改网页端，服务端实例必须使用同一任务 worktree 构建的网页产物。

## 客户端交付

Web 客户端从任务 worktree 构建并交付启动命令或构建产物。

```sh
npm ci --prefix apps/web
npm run build --prefix apps/web
```

桌面客户端需要同时构建桌面前端和 Tauri 客户端，具体平台命令以任务记录为准。交付内容应包含使用的服务端地址、启动方式、构建产物路径和已验证的功能路径。Android 客户端记录 APK 路径、安装命令、设备或模拟器要求以及服务端地址。

客户端验收期间不要切换回主工作区构建，以免把主分支内容与任务内容混淆。

## 自我验收与交付

实现完成后检查以下项目。

- 任务记录中的验收条件逐项有证据。
- 测试命令来自任务 worktree，且记录真实退出状态。
- `git diff --check` 通过，变更只覆盖任务范围。
- Bug 修复包含回归测试，或任务记录说明不可自动化的原因。
- 服务端改动有独立运行实例和停止方式。
- 客户端改动有任务 worktree 的构建或运行入口。
- 账本状态改为 `DELIVERED`，记录交付时间、分支、worktree 和验收入口。

交付消息应包含任务 ID、类型、摘要、分支、worktree、任务记录、验收命令、服务端地址或客户端产物、已知未验证项和停止服务命令。此时保持任务分支和 worktree，等待用户验收。

## 用户确认后的合并与清理

用户明确确认后才执行以下步骤。

```sh
./scripts/local.py stop
cd <main-checkout>
git status --short --branch
git switch main
git merge --ff-only codex/<type>-<short-name>-<yyyymmdd>
git worktree remove ../we-note-<task-id>
git branch -d codex/<type>-<short-name>-<yyyymmdd>
git status --short --branch
```

如果基线分支在交付期间已经前进，先保留任务 worktree，处理冲突并重新运行验收，再使用适合仓库历史的合并方式。发现未预期的未提交文件、未停止的任务服务或合并冲突时暂停清理，保护现场并在任务记录中记录原因。

合并完成后将账本状态改为 `MERGED`，写入合并提交、清理时间和最终验证命令。确认 worktree 列表与分支列表中已经没有该任务的残留。

## 评审与未完成任务

代码评审、设计讨论和状态查询可以直接阅读任务记录和差异，不需要重新创建 worktree。用户要求修改时沿用原分支和 worktree，新增测试或修复现有测试后重新交付。需求发生变化且超出原范围时，更新任务记录和账本，必要时拆分新任务。
