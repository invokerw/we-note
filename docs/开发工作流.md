# WeNote 开发工作流

本流程把用户需求落实为可追踪的开发账本、单任务记录和独立交付环境，适用于功能开发、Bug 修复、重构、测试、文档和工程维护。

## 任务分类

| 类型 | 适用范围 | 必要证据 |
| --- | --- | --- |
| `feature` | 新功能、接口或用户能力 | 新行为测试，必要时补充文档和端到端验收 |
| `bugfix` | 已确认的错误、回归或数据问题 | 能复现问题的失败测试，以及修复后的回归通过证据 |
| `refactor` | 保持行为不变的结构调整、性能或可维护性改进 | 受影响范围的回归测试和行为对照 |
| `test` | 测试夹具、测试基础设施或覆盖率改进 | 新增测试能够在目标入口执行 |
| `docs` | 产品、接口、开发或运维文档 | 链接、示例、命令和术语可验证 |
| `chore` | 构建、依赖、脚本、配置和其他工程维护 | 对应构建、静态检查或运行验证 |

需求同时涉及多个类型时，选择主要目标作为主类型，并在任务记录中列出其他影响面。

## 账本与任务记录

`docs/开发账本.md` 是任务索引和生命周期记录。每项任务使用稳定 ID，建议格式为 `<TYPE>-YYYYMMDD-<short-name>`，其中 `TYPE` 使用大写分类名，例如 `FEAT-20261123-share-assets` 或 `FIX-20261123-sync-cursor`。

任务开始时新增账本条目，并创建 `docs/tasks/<任务 ID>.md`。任务记录至少包含用户原始需求、问题或目标、范围、明确排除项、影响端、用户选定的验收方式、验收条件、测试命令、基线提交、分支、worktree、服务端和客户端交付方式。记录模板见 [任务记录模板](../.codex/skills/wenote-development/references/任务记录模板.md)。

任务记录按时间追加验证证据。每次验收记录实际命令、退出状态、关键输出、未验证项和下一步。不要用“已测试”替代命令和结果。

状态的进入和离开条件见[开发账本](开发账本.md)。

## 新窗口开始开发

用户已指定本任务的验收方式时，把选择写入任务记录。否则先请用户在「1. 主分支验收」和「2. 任务分支验收」中选择，收到答复再开工。

新窗口接到具体开发任务时，检查当前分支、工作区和已有 worktree。确认基线分支和用户未提交的无关改动后，为任务生成稳定 ID。

```sh
git status --short --branch
git worktree list
git switch main
git worktree add -b codex/<type>-<short-name>-<yyyymmdd> ../we-note-<task-id> main
```

如果主工作区存在用户未提交的改动，保留它们，不把它们带入任务。若任务需要从其他基线开始，在任务记录中写明基线提交。

在新 worktree 中先更新账本和任务记录，再写实现代码。任务记录的基线提交、分支和 worktree 路径必须与 Git 实际状态一致。

## TDD 开发循环

采用红、绿、重构的循环。红阶段让测试准确暴露需求或 Bug，绿阶段用最小实现通过测试，重构阶段在全绿基础上整理结构并保持行为契约。

1. 阅读相关实现、既有测试、产品设计和接口文档，确认任务边界。
2. 把验收条件转成最小可执行测试。Bug 修复先加入回归测试，功能开发先覆盖成功路径和关键失败路径。
3. 运行聚焦测试并确认它因预期原因失败。把失败命令和输出摘要写入任务记录。
4. 编写能够让测试通过的最小实现，保持已有调用方的行为契约。
5. 重新运行聚焦测试，再运行受影响模块的回归测试。需要时补充跨端、协议、构建或端到端测试。
6. 在测试全绿后进行必要重构，再重复相关测试。运行 `git diff --check`，检查任务记录和账本也在交付范围内。

文档或配置任务可以使用链接检查、格式检查、构建和启动验证代替代码测试。无法自动化的验收项必须写出人工步骤和观察结果。

## 独立服务端验收

服务端改动必须从任务 worktree 启动独立实例。使用任务专用端口，避免占用主工作区的服务。仓库自带的本地入口从当前 worktree 构建网页和 API。

```sh
cd ../we-note-<task-id>
./scripts/local.py start --port <unique-port>
./scripts/local.py status
curl -fsS http://127.0.0.1:<unique-port>/healthz
```

服务端的构建产物、SQLite 数据、PID 和日志必须留在任务 worktree 对应的运行目录。交付时记录服务地址、PID、日志路径、测试账户或初始化步骤和停止命令。验收期间保持该实例可用，返工后从原 worktree 重建并重启。用户确认通过后停止该实例。

如果任务只修改服务端，可以交付独立服务地址和 API 验收命令。如果同时修改网页端，服务端实例必须使用同一任务 worktree 构建的网页产物。

## 客户端交付

Web 客户端从任务 worktree 构建并交付启动命令或构建产物。

```sh
npm ci --prefix apps/web
npm run build --prefix apps/web
```

桌面客户端需要同时构建桌面前端和 Tauri 客户端，具体平台命令以任务记录为准。交付内容应包含使用的服务端地址、启动方式、构建产物路径和已验证的功能路径。Android 客户端记录 APK 路径、安装命令、设备或模拟器要求以及服务端地址。

客户端验收期间不要切换回主工作区构建，以免把主分支内容与任务内容混淆。

## 自审、提交与合并

每轮测试通过后按 [skill 的自审步骤](../.codex/skills/wenote-development/SKILL.md#测试通过后自审)复查本轮差异，把发现的问题、采取的优化和复测结果写入任务记录。在任务 worktree 暂存本轮文件，检查 `git diff --cached --check`，自审通过后提交。

合并时机由本任务的选择决定。方式 1 在每轮自审通过后合并，方式 2 在用户明确确认该轮任务分支提交通过后合并。

合并时，在检出 `main` 的工作区运行 `git merge --ff-only "$task_branch"`，其中 `task_branch` 是本轮任务分支名。若分支已分叉，先在原 worktree 合入最新本地 `main`，解决冲突并验证集成后的改动。方式 2 若有影响验收行为的修改，在任务分支重新交付确认，再快进合并。保留两个工作区中的用户改动。将 `task_commit` 设为本轮通过验证的任务分支提交号，合并后用 `git merge-base --is-ancestor "$task_commit" main` 验证本轮任务提交已合入。

## 用户验收和返工

交付时给出所选验收方式、本轮受测提交号、验收分支、worktree、测试和自审结论，以及可直接使用的验收步骤。需要服务或客户端的任务，同时给出该版本的服务地址或客户端产物。

用户提出修改时，把反馈和复现步骤记入原任务记录。在原 worktree 同步 `main` 后修改，每轮重新测试、自审、必要复测并提交。方式 1 合入 `main` 后交付，方式 2 继续在原 worktree 交付。更新服务或客户端，交付新提交号供用户再验。每轮交付后继续保留该 worktree 和分支。

## 验收通过后的清理

用户明确确认当前版本通过后，检查任务 worktree 的 Git 状态、需要留存的验收数据或产物，并确认 `git merge-base --is-ancestor "$task_branch" main` 成功。若有尚待交付的修改，先完成对应轮次的验证与交付。

仅对本任务启动的服务，从任务 worktree 执行 `./scripts/local.py stop`。从主工作区运行 `git worktree remove "$task_worktree"` 和 `git branch -d "$task_branch"`。核对清理结果后，在主工作区提交账本与任务记录的最终状态、已验收提交号和清理时间。
